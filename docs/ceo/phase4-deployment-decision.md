### Munger 逆向检验：有什么理由不部署？

1. **内存存储 = 数据全丢。** 服务重启后用户面试记录归零。
   - 反驳：MVP 阶段可接受。种子用户知道这是测试版。Supabase 迁移列为部署后 P0。
2. **CORS 全开 = 安全隐患。** 任何域名都能调用 API。
   - 反驳：部署时必须收紧为实际域名。这是部署 checklist 第一项，不是"后续再做"。
3. **没有速率限制 = 可能被刷。** 恶意调用导致 OpenAI 账单爆炸。
   - 反驳：Cloudflare Workers 自带基础 DDoS 防护。部署后第一周加 slowapi 速率限制。
4. **FastAPI 跑在 Cloudflare Workers 上？** Python 不是 Workers 原生运行时。
   - 反驳：需要验证。如果 Workers 不支持 FastAPI，备选方案是 Fly.io 免费层或 Railway。这是部署阶段的第一个技术验证点。

### 最终判定

**✅ GO — 批准进入 Phase 4 部署阶段。**

理由：
- 5/5 核心维度通过，技术债在可控范围内
- 时间窗口紧迫（校招季 3-6 月），每拖一天都是浪费
- MVP 的目标是"能跑通 + 能演示"，不是"完美无缺"
- Day 1 心态：先上线，再迭代

**附加硬约束：**
- 部署前必须收紧 CORS（不可商量）
- 部署后 48 小时内验证 OpenAI API 调用正常
- 部署后 1 周内完成 Supabase 持久化迁移

## 二、部署策略

### 分阶段部署（推荐）

不做一次性部署。原因：前后端耦合度低，分开部署可以逐步验证，降低排查成本。

**阶段 1：后端先行（Day 1-2）**

关键问题：FastAPI（Python）能否直接跑在 Cloudflare Workers 上？Workers 原生运行时是 V8（JavaScript/WASM），不是 Python。

- **方案 A（首选）：** 使用 Cloudflare Workers + Python 支持（2024 年已推出 Python Workers beta）。如果 FastAPI 兼容性好，直接部署。
- **方案 B（备选）：** 将后端部署到 Fly.io 免费层（256MB RAM，3 个共享 CPU VM）。FastAPI 原生运行，零改造成本。
- **方案 C（保底）：** Railway 免费层（$5 信用额度/月）。

执行步骤：
1. 先尝试方案 A：`wrangler deploy` 测试 FastAPI 是否能跑通
2. 如果 10 分钟内跑不通，立即切方案 B（Fly.io）
3. 部署后验证 `/health` 端点返回 `{"status": "ok"}`
4. 验证 OpenAI API 调用链路：后端 → OpenAI → 返回结果

**阶段 2：前端跟进（Day 2-3）**

前端部署到 Cloudflare Pages，这个没有争议——Next.js + Pages 是成熟组合。

执行步骤：
1. `npm run build` 确认构建通过
2. 配置环境变量：`NEXT_PUBLIC_API_URL` 指向阶段 1 部署的后端地址
3. `npx wrangler pages deploy` 部署
4. 验证首页加载、API 连通性

**阶段 3：端到端验证（Day 3-4）**

完整跑通核心流程：上传简历 → 生成面试题 → 回答 → 评分 → 生成报告。

验证清单：
- [ ] 简历上传（TXT）→ 解析成功
- [ ] 面试题生成 → 返回 4 部分题目
- [ ] 答案提交 → 返回评分 + 反馈
- [ ] 报告生成 → 返回综合评估
- [ ] 错误场景：空文件、超大文件、无效格式

### 灰度发布：不需要

理由：
- 种子用户 < 10 人，全量发布 = 灰度发布
- 没有历史用户需要保护
- 出问题直接回滚，影响面极小

### 域名策略：先用默认域名

- **前端：** `interview-copilot.pages.dev`（Cloudflare Pages 默认）
- **后端：** `interview-copilot-api.xxx.workers.dev`（Workers 默认）或 Fly.io 默认域名
- **自定义域名：** 暂不购买。等种子用户验证通过、确认项目值得继续后再考虑
- **理由：** 域名是虚荣指标。对于简历项目，`pages.dev` 域名完全够用。省下的 ¥50-100/年 可以多调 1000 次 OpenAI API

## 三、Pre-Mortem：假设部署失败了

**场景：现在是 2026 年 3 月 13 日，Phase 4 部署一周了，项目被判定为失败。**

### 失败模式 1：API 不通 — 前后端无法通信

**症状：**
- 前端页面加载正常，但所有 API 调用返回 CORS 错误或 502
- 用户看到"网络错误"提示，无法进行任何操作
- 控制台满屏红色错误

**根本原因：**
- CORS 配置错误：收紧后忘记加 `pages.dev` 域名
- 后端部署失败：FastAPI 在 Workers 上不兼容，没有及时切备选方案
- 环境变量遗漏：`OPENAI_API_KEY` 没有配置到生产环境

**概率：** 中高（40%）— 这是最可能出现的问题

**预防措施：**
- ✅ 部署后立即用 curl 测试每个端点（不依赖前端）
- ✅ CORS 白名单包含：`*.pages.dev` + `localhost:3000`（开发）
- ✅ 准备 Fly.io 备选方案，10 分钟内可切换
- ✅ 环境变量 checklist：逐项核对，不遗漏

**止损方案：** 如果 Workers 方案 2 小时内跑不通，立即切 Fly.io。不要死磕。

### 失败模式 2：OpenAI API Key 泄漏

**症状：**
- OpenAI 账单突然暴增（¥100+/天）
- 收到 OpenAI 异常使用告警邮件
- API Key 出现在 GitHub 公开仓库或前端代码中

**根本原因：**
- `.env` 文件被误提交到 Git
- 前端代码中硬编码了 API Key（`NEXT_PUBLIC_` 前缀暴露到客户端）
- 后端日志打印了请求头（包含 Key）

**概率：** 低（10%）— 但后果严重

**预防措施：**
- ✅ `.gitignore` 已包含 `.env`（已确认）
- ✅ API Key 只存在后端环境变量中，前端通过后端代理调用
- ✅ 部署前全局搜索 `sk-` 确认无硬编码 Key
- ✅ OpenAI 后台设置月度消费上限（¥20）
- ✅ 启用 OpenAI 消费告警（¥10 时邮件通知）

**止损方案：** 发现泄漏后 5 分钟内：① 在 OpenAI 后台 revoke Key ② 生成新 Key ③ 更新生产环境变量 ④ 检查 Git 历史，必要时 force push（仅限非 main 分支）

### 失败模式 3：用户数据丢失（内存存储崩溃）

**症状：**
- 用户完成面试后刷新页面，数据消失
- 服务重启后所有历史记录归零
- 用户投诉"做了半小时面试，结果没了"

**根本原因：**
- 当前使用内存存储（Python dict），服务重启即清空
- Cloudflare Workers 无状态，每次请求可能在不同实例
- 没有持久化层，面试会话数据只存在于进程内存

**概率：** 高（70%）— 这是已知技术债，不是意外

**预防措施：**
- ✅ 种子用户明确告知"测试版，数据可能丢失"
- ✅ 报告生成后提示用户截图保存
- ✅ 部署后 1 周内完成 Supabase 持久化迁移（P0 优先级）
- ✅ 迁移前：每次面试结束自动生成报告，减少数据丢失影响

**止损方案：** 如果用户反馈强烈，48 小时内紧急接入 Supabase。schema.sql 已就绪，迁移工作量约 1 天。

### 失败模式 4：成本失控

**症状：**
- OpenAI 月账单超过 ¥20 上限
- 被恶意刷接口，单日调用量 > 1000 次
- 免费额度用完后 Cloudflare 开始计费

**概率：** 低（15%）— 种子用户 < 10 人，正常使用不会超限

**预防措施：**
- ✅ OpenAI 后台设置硬上限 ¥20/月
- ✅ 部署后第一周加速率限制（slowapi：10 次/分钟/IP）
- ✅ Cloudflare Workers 免费额度 100K 请求/天，远超需求
- ✅ 每周一检查 OpenAI 账单 + Cloudflare 用量

**止损方案：** 账单超 ¥15 时自动告警。超 ¥20 时关闭 API 调用，返回"服务暂停维护"。

### 失败模式 5：没人用

**症状：**
- 部署一周后，0 个种子用户完成完整面试
- 分享链接后无人点击
- 用户打开首页就离开，转化率 < 5%

**概率：** 中（30%）— 简历项目的常见结局

**预防措施：**
- ✅ 不依赖"自然流量"，主动邀请 5-10 名目标用户
- ✅ 提供 1 对 1 引导（微信群/私聊），降低使用门槛
- ✅ 首页 3 秒内传达核心价值："上传简历 → AI 模拟面试 → 获得评分报告"
- ✅ 即使没人用，项目本身作为简历展示仍有价值

**止损方案：** 如果 2 周内 < 3 人完成面试，项目转为纯简历展示模式，不再投入开发资源。

## 四、成本控制策略

### 硬约束：¥20/月上限

这是不可突破的红线。超过即暂停服务。

### API 调用上限

| 环境 | 上限 | 理由 |
|------|------|------|
| 开发环境 | 50 次/天 | 开发测试用 mock 数据为主 |
| 生产环境 | 200 次/天 | 假设 20 用户 × 10 次 API 调用/面试 |
| 单用户 | 20 次/天 | 防止单人刷接口 |

### 成本明细估算

| 项目 | 单价 | 月用量（预估） | 月成本 |
|------|------|---------------|--------|
| OpenAI API（简历解析） | ~¥0.02/次 | 100 次 | ¥2 |
| OpenAI API（答案评估） | ~¥0.03/次 | 200 次 | ¥6 |
| OpenAI API（报告生成） | ~¥0.02/次 | 50 次 | ¥1 |
| Cloudflare Workers | 免费 | < 100K 请求 | ¥0 |
| Cloudflare Pages | 免费 | < 500 构建 | ¥0 |
| Supabase | 免费 | < 500MB | ¥0 |
| **总计** | | | **~¥9/月** |

安全余量：¥20 - ¥9 = ¥11，足够应对 2 倍流量波动。

### 监控告警配置

| 指标 | 告警阈值 | 动作 |
|------|---------|------|
| OpenAI 日消费 | > ¥1 | 邮件通知 |
| OpenAI 月消费 | > ¥15 | 邮件 + 限流 50% |
| OpenAI 月消费 | > ¥20 | 自动暂停 API 调用 |
| Workers 日请求量 | > 50K | 邮件通知（检查是否被刷） |
| 单 IP 请求频率 | > 10 次/分钟 | 自动限流 |

### 每周成本审计流程

**每周一上午执行（5 分钟）：**
1. 登录 OpenAI 后台 → 查看本周消费 → 记录到 `logs/cost-weekly.md`
2. 登录 Cloudflare Dashboard → 查看 Workers/Pages 用量
3. 如果周消费 > ¥5 → 分析原因 → 决定是否调整限流策略
4. 如果月消费趋势 > ¥20 → 立即限流或暂停非核心 API

## 五、用户获取策略（部署后第一周）

3. 反馈能指导迭代方向（需求验证）

### 渠道策略

| 渠道 | 目标人数 | 方式 | 优先级 |
|------|---------|------|--------|

| 小红书 | 0-1 人 | 发笔记"用 AI 练面试"（测试渠道效果） | P3 |

### 种子用户画像

- 2026 届本科/研究生，计算机相关专业
- 正在准备校招（3-6 月）
- 有面试焦虑，缺乏练习机会
- 愿意花 20 分钟尝试新工具

- **免费使用：** 内测期间完全免费（本来就免费）
